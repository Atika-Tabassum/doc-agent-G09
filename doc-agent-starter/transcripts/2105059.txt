ASSISTANT:
Robust get_data.sh Pattern

```bash
#!/usr/bin/env bash
set -euo pipefail
IFS=$'\n\t'

# ---- Config ----
DATA_URL="${DATA_URL:-https://example.com/corpus.tar.gz}"
DEST_DIR="${DEST_DIR:-./data}"
ARCHIVE_NAME="corpus.tar.gz"
ARCHIVE_PATH="${DEST_DIR}/${ARCHIVE_NAME}"
EXPECTED_SHA256="${EXPECTED_SHA256:-}"   # set this, or fetch a .sha256 sidecar
EXTRACT_DIR="${DEST_DIR}/corpus"
MARKER_FILE="${EXTRACT_DIR}/.download_complete"
MAX_RETRIES=3

log()  { printf '[%s] %s\n' "$(date -u +'%Y-%m-%dT%H:%M:%SZ')" "$*" >&2; }
die()  { log "ERROR: $*"; exit 1; }

mkdir -p "$DEST_DIR"

# ---- Idempotency guard ----
if [[ -f "$MARKER_FILE" ]]; then
    log "Corpus already present at $EXTRACT_DIR (marker found). Skipping."
    exit 0
fi

# ---- Download with retries ----
download() {
    local attempt=1
    while (( attempt <= MAX_RETRIES )); do
        log "Download attempt $attempt/$MAX_RETRIES..."
        if curl --fail --location --show-error --silent \
                --retry 2 --retry-delay 5 \
                --connect-timeout 10 --max-time 600 \
                -o "${ARCHIVE_PATH}.part" "$DATA_URL"; then
            mv "${ARCHIVE_PATH}.part" "$ARCHIVE_PATH"
            return 0
        fi
        log "Attempt $attempt failed."
        ((attempt++))
        sleep $((attempt * 3))
    done
    return 1
}

if [[ -f "$ARCHIVE_PATH" ]]; then
    log "Archive already downloaded, verifying before reuse."
else
    download || die "Failed to download after $MAX_RETRIES attempts."
fi

# ---- Checksum verification ----
verify_checksum() {
    [[ -z "$EXPECTED_SHA256" ]] && { log "No checksum configured, skipping verification."; return 0; }
    local actual
    actual=$(sha256sum "$ARCHIVE_PATH" | awk '{print $1}')
    if [[ "$actual" != "$EXPECTED_SHA256" ]]; then
        log "Checksum mismatch: expected=$EXPECTED_SHA256 actual=$actual"
        rm -f "$ARCHIVE_PATH"   # remove corrupt file so retry doesn't reuse it
        return 1
    fi
    log "Checksum OK."
}

verify_checksum || die "Checksum verification failed; archive removed."

# ---- Extract ----
mkdir -p "$EXTRACT_DIR"
tar -xzf "$ARCHIVE_PATH" -C "$EXTRACT_DIR" --strip-components=1 \
    || die "Extraction failed."

# ---- Mark complete (atomic-ish) ----
touch "$MARKER_FILE"
log "Corpus ready at $EXTRACT_DIR"

```

### Key principles

**Fail fast and loud**
`set -euo pipefail` catches unset vars, pipe failures, and non-zero exits instead of silently continuing.

**Idempotency via marker file, not just file existence**
Checking `-f archive.tar.gz` alone is dangerous — a partial/corrupt download looks "present." A marker written only after checksum+extraction succeed is your real "done" signal.

**Atomic downloads**
Download to `.part`, then `mv` into place. Prevents a killed script from leaving a half-written file that a future run trusts.

**Checksums, always**
Pull `EXPECTED_SHA256` from env/config or a `.sha256`/`.sha256sum` sidecar hosted next to the corpus. On mismatch, delete the bad file — don't leave it for the next run to "successfully" find.

**Bounded retries with backoff**
`curl --retry` handles transient network blips; your own loop handles total failures (server down, bad URL) without hanging forever.

**Structured logging to stderr**
Keeps stdout clean if other pipeline stages consume this script's output.

### Extras worth adding depending on your pipeline

* Lock file (`flock`) if this script might run concurrently in CI or multiple agents.
* Disk space check before download (`df` on `$DEST_DIR`) if the corpus is large.
* Version pinning: embed a version/date in the URL or marker filename so re-running after a corpus update doesn't silently skip the new data.
* Dry-run flag (`--dry-run`) for pipeline testing without network calls.
* Cleanup trap: `trap 'rm -f "${ARCHIVE_PATH}.part"' EXIT` to clear partial files on interrupt.

## Structuring for Safe Re-Runs

The core idea: never let the "final" state be observable in a partially-written form. Every re-run should either see a complete, verified prior result and skip, or see nothing and start clean — never something in between.

### 1. Stage everything, then atomically promote

Never write directly into the destination path. Work in a temp/staging location, verify, then move into place with a single atomic operation.

```bash
STAGING_DIR="${DEST_DIR}/.staging.$$"
FINAL_DIR="${DEST_DIR}/corpus"

mkdir -p "$STAGING_DIR"
# ... download, extract, verify into $STAGING_DIR ...

# Atomic promotion (rename is atomic on same filesystem)
rm -rf "${FINAL_DIR}.old"                    # cleanup from any prior interrupted swap
[[ -d "$FINAL_DIR" ]] && mv "$FINAL_DIR" "${FINAL_DIR}.old"
mv "$STAGING_DIR" "$FINAL_DIR"
rm -rf "${FINAL_DIR}.old"

```

If the script dies mid-download, `$FINAL_DIR` is untouched — old good data (if any) is still there, and the next run just retries staging.

### 2. Use a state file with content hash, not just presence

A marker file that only says "I ran" isn't enough — it can't tell you what it downloaded. Store the identity of the completed data so re-runs can detect drift:

```bash
STATE_FILE="${FINAL_DIR}/.fetch_state.json"

write_state() {
    cat > "$STATE_FILE" <<EOF
{
  "url": "$DATA_URL",
  "sha256": "$actual_checksum",
  "fetched_at": "$(date -u +%FT%TZ)",
  "script_version": "1.2"
}
EOF
}

is_up_to_date() {
    [[ -f "$STATE_FILE" ]] || return 1
    local prev_url prev_sha
    prev_url=$(jq -r '.url' "$STATE_FILE" 2>/dev/null) || return 1
    prev_sha=$(jq -r '.sha256' "$STATE_FILE" 2>/dev/null) || return 1
    [[ "$prev_url" == "$DATA_URL" && "$prev_sha" == "$EXPECTED_SHA256" ]]
}

if is_up_to_date; then
    log "Existing corpus matches requested URL/checksum. Skipping."
    exit 0
fi

```

This means if you bump `DATA_URL` or `EXPECTED_SHA256` later (new corpus version), the script correctly re-fetches instead of trusting a stale marker.

### 3. Lock against concurrent runs

If this could be triggered by multiple agents/CI jobs at once, guard it:

```bash
LOCK_FILE="${DEST_DIR}/.fetch.lock"
exec 200>"$LOCK_FILE"
flock -n 200 || die "Another fetch is already in progress."

```

Everything after this line only runs if the lock was acquired; it's released automatically when the script exits.

### 4. Clean up on interrupt, not just on success

```bash
cleanup() {
    rm -rf "$STAGING_DIR" "${ARCHIVE_PATH}.part"
}
trap cleanup EXIT INT TERM

```

This guarantees a Ctrl-C or CI timeout doesn't leave half-written staging directories lying around to confuse the next invocation.

### 5. Verify before promote, never after

Checksum and sanity-check (e.g. expected file count, non-empty, valid archive) inside the staging directory, before the atomic move. Once something is in `$FINAL_DIR`, a re-run should be able to trust it exists.

```bash
[[ $(find "$STAGING_DIR" -type f | wc -l) -gt 0 ]] || die "Staged corpus is empty, aborting promotion."

```

### Putting it together — re-run decision tree

```text
run script
├── lock acquired?
│   └── no → exit (another run owns it)
├── state file matches requested url+sha?
│   └── yes → skip, exit 0
├── download to staging (atomic .part → archive)
├── verify checksum
│   └── fail → delete staged files, exit 1 (old FINAL_DIR untouched)
├── extract + sanity check in staging
├── atomically promote staging → final
└── write new state file

```

With this structure, running the script 1 time or 50 times in a row, or killing it mid-run repeatedly, always converges to the same correct end state — which is really the definition of idempotent.

One more thing worth adding: a `--force` flag that bypasses the state-file check, for when you deliberately want to re-fetch despite a match (corpus updated at the same URL/hash accidentally, e.g.).

### File-system / I/O

* **Empty files** — 0 bytes. Already caught by `min_chars`, but worth a distinct log message vs. "too short after normalization" so you can tell "corrupt/truncated" apart from "genuinely short."
* **Zero-byte vs. whitespace-only files** — a file with only newlines/spaces passes the byte-count check but should still be filtered; `min_chars` after `.strip()` handles this, but double check it's applied before the length check, not after.
* **Symlinks / broken symlinks** — `Path.glob` follows symlinks by default; a broken one raises `FileNotFoundError` on read. Catch this explicitly rather than letting a generic `OSError` swallow it silently.
* **Permission errors** — file exists but isn't readable (common after partial extraction with wrong umask). Distinct from "file missing."
* **Directories matching the glob pattern** — if pattern is loose (e.g. `**/*`), you can pick up directories, not just files. Guard with `path.is_file()`.
* **Extremely large single files** — if the corpus mixes "one file per page" with an occasional 500MB outlier (e.g. a merged dump), `read_text()` loads it all into memory. Consider a size check and either stream it or route it to a different handler.
* **Duplicate doc_ids** — if pattern can match the same logical file twice (e.g. via multiple glob patterns, or case-insensitive filesystems where `Doc.txt` and `doc.txt` both exist), you'll silently get two `Page` objects with the same or colliding ids. Worth a dedupe check with a warning.
* **Non-deterministic file order** — `sorted()` handles this for `Path.glob`, but confirm your filesystem's path strings sort the way you want (numeric filenames like `page2.txt` vs `page10.txt` sort lexically, not numerically — matters if page order is semantically meaningful downstream).

### Encoding / text-level

* **Mixed encodings within one corpus** — different files decode correctly under different encodings. Your fallback chain handles this per-file, but log which encoding was actually used per file (already in `Page.encoding_used`) so you can audit for anomalies later — a corpus that's 95% UTF-8 and 5% something else is a red flag worth surfacing, not just silently handling.
* **Byte sequences that decode "successfully" but are wrong** — this is the dangerous one. `cp1252` will happily decode almost any byte string without raising an error — it just produces garbage silently. A file that's actually legacy Bangla-font bytes could decode as valid-looking `cp1252` mojibake and pass through with no exception at all. Consider a post-decode sanity check: e.g., if `normalize_form == "NFC"` and the target is Bangla, verify a minimum proportion of characters fall in the Bengali Unicode block (`U+0980`–`U+09FF`); if a file decodes but has near-zero Bengali code points despite being expected to be Bangla, flag it rather than silently accepting.
* **BOM handling** — `utf-8-sig` strips a BOM if present, but if `utf-8` is tried first and the file has a BOM, you'll get a stray `\ufeff` character at the start of the text that survives normalization. Either always try `utf-8-sig` before plain `utf-8`, or strip `\ufeff` explicitly post-decode.
* **Invalid/unassigned Unicode code points** — rare but possible from bad scraping (private-use-area characters, unassigned code points). Decide whether to strip these or keep them; silently passing them to a tokenizer downstream can cause cryptic vocab errors.
* **Unicode normalization changing length/offsets** — if any downstream component relies on character offsets into the original file (e.g. for provenance/highlighting), normalizing before storing offsets will desync them. If you need offset-fidelity, normalize a copy for processing but keep raw text (or an offset-mapping) alongside.
* **Right-to-left / bidi marks** — less relevant for Bangla itself (LTR), but if the corpus is multilingual and some documents contain Arabic/Urdu passages mixed in, bidi control characters can cause rendering/tokenization oddities. Worth deciding whether to normalize/strip them.
* **Null bytes** — occasionally show up in corrupted text extractions (e.g. bad PDF→text conversion). `read_text` won't error on them, but many downstream libraries (databases, some tokenizers) choke on `\x00`. Strip explicitly if this corpus was ever machine-converted from another format.

### Corpus-semantic edge cases (specific to your pipeline)

* **Code-mixed / wrong-language documents** — a file that's supposed to be Bangla but is actually English (or another language) due to upstream scraping errors. You flagged this in `provenance.md` — consider running a language-ID check (`fastText lid.176` or similar) inside `load_pages()` itself, with an `expected_lang` param, so mislabeled files get flagged rather than silently entering the pipeline as "Bangla."
* **Romanized Bangla mixed with script Bangla** — a file entirely in Latin-script transliteration will pass every check above (valid UTF-8, valid Unicode, non-empty) but is semantically a different kind of data than script Bangla. If your Bengali-Unicode-block-ratio check from above is in place, this would also get flagged, which is useful — decide whether you want to keep, separate, or drop these.
* **Duplicate content under different filenames** — two pages with identical or near-identical text (common in scraped/re-published news corpora). Not a load-time crash, but worth at least a content-hash field on `Page` so a downstream dedup step can act on it without re-reading files.
* **Page-boundary ambiguity** — if it turns out (per your earlier note) that some files actually contain multiple logical "pages" separated by a delimiter (e.g. form-feed `\x0c`, or a custom marker), a naive one-file-one-page assumption silently merges them into one oversized `Page`. * **Truncated downloads that extracted "successfully"** — your `get_data.sh` verifies the archive checksum, but if extraction itself is interrupted (`disk full` mid-`tar -xzf`), you could get files that are truncated mid-write but still exist and are non-empty. ## Deciding the Return Type for load_pages()

This comes down to a few concrete tradeoffs, not a style preference. Walk through them in order — each one narrows the choice.

### 1. Memory: does the whole corpus fit in RAM at once?

This is the first fork, and it's the one that decides between `list[Page]` and `Iterator[Page]`.

* **Small/medium corpus (fits comfortably in memory)** → `list[Page]`. Simpler for callers: they can `len()` it, index into it, iterate multiple times, pass it to something that needs random access (e.g. a retriever building an index).
* **Large corpus, or corpus size unknown/unbounded** → `Iterator[Page]` (generator). You already sketched this as `iter_pages()` — but consider whether you actually need two functions, or whether `load_pages()` should just always return a generator and callers who want a list do `list(load_pages(...))` themselves. Two functions duplicate logic and drift out of sync; one generator function is usually the better default, with the list-conversion pushed to the caller.

*Rule of thumb:* if you're not sure, default to a generator. It's strictly more flexible — a caller can always materialize it into a list, but you can't "un-materialize" a list back into streaming behavior. The cost is real though: single-pass only, no `len()`, no indexing, and generators make certain error-handling patterns awkward (see #3).

### 2. Does the caller need summary/aggregate info alongside the pages?

Your current design raises `CorpusLoadError` if all files are skipped, and logs warnings for individual skips — but the caller never sees how many were skipped, or why, unless they're reading logs. If downstream code (or a human running the pipeline) needs to know "loaded 940/1000 files, 60 skipped: 40 too-short, 15 encoding-failure, 5 wrong-language," a bare `list[Page]` or `Iterator[Page]` can't carry that.

Two ways to handle it:

* **Simple:** return `list[Page]` only, keep skip-accounting in logs. Fine if this is an internal pipeline stage and logs are actually monitored.
* **Richer:** wrap the result in a small result object:

```python
@dataclass
class LoadResult:
    pages: list[Page]
    skipped: list[SkipRecord]   # path + reason
    total_files_seen: int

    @property
    def success_rate(self) -> float:
        return len(self.pages) / self.total_files_seen if self.total_files_seen else 0.0

```

This is worth it if skip-rate is itself a signal you'll want to alert on (e.g. "if >5% of files fail to load, something upstream broke") rather than just debug-log noise. Given your provenance/encoding concerns earlier in this conversation, I'd lean toward this — a silent 15% skip rate on a Bangla corpus with known legacy-encoding risk is exactly the kind of thing that should be visible to the caller, not buried in logs.

### 3. Streaming vs. batch changes how errors surface

This is the part people usually get wrong when picking a generator.

With `list[Page]`, `load_pages()` runs to completion before returning — all-or-nothing exceptions (like your "raise if everything skipped" check) are easy: you have the full picture before you hand anything back.

With `Iterator[Page]`, the function returns immediately (generators don't execute until iterated), and errors on file #800 of 1000 surface midway through the caller's loop — after they've already processed 799 pages. If the caller does:

```python
for page in load_pages(corpus_dir):
    process(page)

```

...and the corpus turns out to be entirely empty or the directory doesn't exist, that `CorpusLoadError` you raise up-front won't fire until the first `next()` call — which is usually fine — but a mid-stream failure (e.g. a manifest mismatch discovered on file 800) is a much messier failure mode to reason about, especially if `process()` has side effects that aren't easily undone.

If you go generator: decide explicitly whether validation (empty corpus, manifest mismatch) happens eagerly at call time or lazily at first iteration, and document it. A common pattern is to do all directory/manifest-level checks synchronously before yielding anything, then yield pages one at a time:

```python
def load_pages(corpus_dir, ...) -> Iterator[Page]:
    root = Path(corpus_dir)
    if not root.is_dir():
        raise CorpusLoadError(...)          # fires immediately, not on first next()
    files = sorted(root.glob(pattern))
    if not files:
        raise CorpusLoadError(...)
    ...
    yield from _generate_pages(files, ...)  # actual streaming happens here

```

This isn't automatic — a plain `def load_pages(): ...` with `yield` inside won't run any code, including the directory check, until first iteration, because the whole function body becomes generator machinery. If you want the up-front checks to run eagerly, you need to split it like above (a regular function that validates, then delegates to an internal generator).

### 4. Do you need typed access, or is a dict/tuple enough?

You've already got `Page` as a dataclass, which is the right call here — resist the temptation to return `list[dict]` or `list[tuple[str, str]]` for "flexibility." A typed dataclass gives you IDE autocomplete, makes `Page.encoding_used` / future fields discoverable, and fails at construction time (not deep in a pipeline) if a required field is missing. Given this is feeding a document-agent pipeline that will likely grow more fields (language confidence, `bengali_char_ratio`, content hash for dedup, page-split flags — several of which came up in the edge-cases list), a dataclass scales; a dict doesn't self-document and typos in keys (`"docid"` vs `"doc_id"`) fail silently.

### Decision matrix

| Corpus size | Need aggregate stats? | Recommended return type |
| --- | --- | --- |
| Small (fits in RAM, < ~100k docs) | No | `list[Page]` |
| Small | Yes | `LoadResult` (pages + skip records) |
| Large / unbounded | No | `Iterator[Page]`, eager validation before first yield |
| Large | Yes | `Iterator[Page]` + separate `.stats` property/object populated as it drains, or a final sentinel/summary yielded — gets awkward; often better to do a cheap pre-scan pass for counts, then stream |

### My recommendation for your case

Given everything discussed in this conversation — Bangla encoding risk, language-mismatch risk, skip-rate as a meaningful signal, and a document-agent pipeline that will likely want to log/alert on corpus health — I'd go with:

```python
def load_pages(corpus_dir, ...) -> LoadResult:
    ...

```

i.e. `list[Page]` wrapped in a small result object, not a bare list and not a generator — unless you already know the corpus will exceed available memory, in which case switch to the eager-validation generator pattern in #3 and move skip-accounting into a mutable stats object the caller can inspect after draining the iterator.

What does the `.egg-info` directory represent, and why does it get generated/tracked when running `pip install -e .`?

ASSISTANT:
`.egg-info` is metadata directory that setuptools generates to describe your package — it's not your code, it's *about* your code.

### What's inside it:

* `PKG-INFO` — package metadata (name, version, author, etc.), essentially a rendered version of your `setup.py`/`setup.cfg`/`pyproject.toml`
* `SOURCES.txt` — list of source files setuptools thinks belong to the package
* `dependency_links.txt` — any extra package index URLs
* `entry_points.txt` — console scripts / entry points your package defines
* `requires.txt` — install dependencies
* `top_level.txt` — top-level importable module/package names
* `installed-files.txt` (sometimes) — files placed on disk during install

### Why `pip install -e .` generates it:

`-e` (editable install) doesn't copy your code into `site-packages` like a normal install would. Instead it needs a way to make your package importable while the source stays in place in your repo. To do that, setuptools:

1. Builds the `.egg-info` metadata directory in your project root (or `src/` if you use a src-layout)
2. Uses that metadata to register the package with pip/setuptools (so `pip show`, `pip list`, dependency resolution, entry points, etc. all work)
3. Adds a `.pth` file or uses an editable-install shim (finder) pointing back at your source directory, so `import yourpackage` resolves to your working copy instead of a `site-packages` copy

So the `.egg-info` directory is essentially the **install-time bookkeeping** that lets pip treat your live source tree as if it were an installed package — dependency info, entry points, and metadata all live there instead of in a separate installed copy.

### Why it shouldn't be tracked in git:

It's a **build artifact**, regenerated automatically every time you run `pip install -e .` or `python setup.py develop`. It's derived entirely from your `setup.py`/`pyproject.toml` plus your source tree — nothing in it is source of truth. Committing it:

* creates merge conflicts on a generated file
* can go stale relative to your actual `setup.py`/`pyproject.toml` and cause confusing installed-vs-actual mismatches
* pollutes diffs

The fix is almost always to add it to `.gitignore`:

```
*.egg-info/

```

If it's already tracked in your repo, remove it with:

```bash
git rm -r --cached *.egg-info

```

then commit the `.gitignore` change.

How do I detect data quality issues (near-duplicates, empty documents, outliers) during EDA for this

ASSISTANT:
For EDA on this page-image dataset, here's how to detect each issue concretely:

### 1. Near-duplicates (perceptual hashing)

Exact hashing (MD5/SHA) only catches byte-identical files. For near-duplicates (same page re-scanned, slightly cropped, recompressed), use perceptual hashing:

```python
import imagehash
from PIL import Image
from collections import defaultdict

def compute_phashes(pages: list[Path]) -> dict[Path, imagehash.ImageHash]:
    return {p: imagehash.phash(Image.open(p)) for p in pages}

def find_near_duplicates(hashes: dict, threshold: int = 5) -> list[tuple]:
    items = list(hashes.items())
    dupes = []
    for i in range(len(items)):
        for j in range(i + 1, len(items)):
            dist = items[i][1] - items[j][1]  # Hamming distance
            if dist <= threshold:
                dupes.append((items[i][0], items[j][0], dist))
    return dupes

```

* `phash` (perceptual hash) is robust to minor resizing/compression, better than `ahash`/`dhash` for scanned docs
* Threshold of ~5 is a reasonable starting point for "likely duplicate"; tune by manually inspecting borderline pairs
* O(n²) comparison is fine up to a few thousand images; beyond that, bucket by hash prefix or use `datasketch` (LSH) to avoid full pairwise comparison

For text targets (if you have OCR'd text alongside images), pair this with text similarity:

```python
from difflib import SequenceMatcher

def text_similarity(a: str, b: str) -> float:
    return SequenceMatcher(None, a, b).ratio()

```

Or better, use MinHash/LSH (`datasketch`) if your dataset is large — pairwise `difflib` doesn't scale.

### 2. Empty/near-empty documents

```python
import numpy as np

def is_blank(img: Image.Image, white_thresh: float = 0.98) -> bool:
    arr = np.array(img.convert("L"))
    white_ratio = (arr > 240).sum() / arr.size
    return white_ratio > white_thresh

def content_density(img: Image.Image) -> float:
    """Fraction of non-white pixels — low value flags near-empty pages."""
    arr = np.array(img.convert("L"))
    return (arr <= 240).sum() / arr.size

```

Plot the distribution of `content_density` across your dataset (histogram) — blank/near-blank pages cluster near zero and are easy to spot as a spike at the low end.

If you have extracted text alongside images, also flag by token count:

```python
def is_empty_text(text: str, min_tokens: int = 3) -> bool:
    return len(text.split()) < min_tokens

```

### 3. Outliers (resolution, aspect ratio, file size)

Pull these into a dataframe and look at distributions rather than eyeballing files:

```python
import pandas as pd

def build_stats_df(pages: list[Path]) -> pd.DataFrame:
    rows = []
    for p in pages:
        img = Image.open(p)
        w, h = img.size
        rows.append({
            "path": p,
            "width": w,
            "height": h,
            "aspect_ratio": w / h,
            "file_size_kb": p.stat().st_size / 1024,
            "mode": img.mode,
        })
    return pd.DataFrame(rows)

df = build_stats_df(pages)
df.describe()  # min/max/mean/std, quick smell test

```

Then flag outliers with IQR or z-score:

```python
def flag_outliers(df: pd.DataFrame, col: str, k: float = 1.5) -> pd.Series:
    q1, q3 = df[col].quantile([0.25, 0.75])
    iqr = q3 - q1
    lower, upper = q1 - k * iqr, q3 + k * iqr
    return (df[col] < lower) | (df[col] > upper)

df["resolution_outlier"] = flag_outliers(df, "width") | flag_outliers(df, "height")
df["filesize_outlier"] = flag_outliers(df, "file_size_kb")

```

Visualize rather than just filtering numerically — a histogram or scatter (width vs. height) usually makes outlier clusters obvious (e.g., a batch of landscape-oriented scans mixed into a portrait-dominant dataset, which often signals a loader bug rather than genuine diversity).

def run_eda(pages: list[Path]) -> dict:
    df = build_stats_df(pages)
    hashes = compute_phashes(pages)
    return {

### Common breakage after merging test files

* **Duplicate fixture names** — if two files each defined a `sample_pages` fixture with different scopes/content, merging silently picks one (pytest resolution order), and tests relying on the other's specific data start failing quietly
* **Import collisions** — merged files often end up with duplicate or now-unused imports; also watch for two test files defining classes/functions with the same name if you flattened modules
* **Fixture scope changes** — if a fixture was `function`-scoped in one file and `module`-scoped in another, and you kept one, tests that relied on fresh state per-test can start leaking state between tests
* **conftest.py placement** — if fixtures used to live in per-file setup and you consolidated into `conftest.py`, check the directory it's in — pytest fixture discovery is path-based, so a `conftest.py` in the wrong directory won't be picked up
* **Mocked paths breaking** — if tests use `monkeypatch`/`mock.patch` on module paths (e.g., `patch("preprocess.some_func")`), refactoring which module something lives in breaks the patch target silently (test passes for the wrong reason, or fails with a confusing `AttributeError`)
* **Test discovery** — run `pytest --collect-only` first to confirm every test you expect is actually being discovered post-merge, before checking pass/fail; a silently un-discovered test (wrong naming convention, `__init__.py` issue) looks identical to "everything passed"
