1. Class C3: Honest Measurement
Core Idea: Ensuring the machine learning evaluation is fair, realistic, and free of data leakage (cheating unintentionally).

What it means in your project:

"Split by document, not page": If a multi-page document is split randomly page-by-page into training and testing sets, pages from the same document end up in both. Since pages in a single document share identical fonts, layouts, scan artifacts, and handwriting/print styles, the model can memorize those visual characteristics. By splitting full documents into training or testing groups, you force the model to evaluate on completely unseen documents.

"Leakage = the same scan in two splits": Data leakage happens if duplicate images/scans of the same original document exist in both the training set and the test set. If this occurs, the evaluation scores will be artificially inflated because the model is tested on data it already saw during training.

2. Class C15: Data as the Lever
Core Idea: Focusing performance improvements on the quality and engineering of the dataset itself (Data-Centric AI), rather than just tweaking model algorithms.

What it means in your project:

This includes gathering the text/image corpus, removing exact or near-duplicate document scans (deduplication) so they don't corrupt the splits, and curating the text representations (like converting OCR/page JSONs into structured ground truth) to make the downstream task effective.

Assistant:
Yes — **you should use the Tesseract hierarchy as the primary grouping mechanism, but you should not rely on `(block_num, par_num, line_num)` alone to establish the final literary reading order.** For your corpus, a secondary spatial sort using the `top`/`y` coordinate is safer.

### Why

`image_to_data()` gives you two different kinds of information:

* **Structural hierarchy**

  * `block_num`
  * `par_num`
  * `line_num`
  * `word_num`
* **Physical position**

  * `left`
  * `top`
  * `width`
  * `height`

The important distinction is that **`block_num` is an OCR segmentation identifier, not a semantic reading-order guarantee**.

For example, imagine a page like:

```text
              কবিতা

      প্রথম পঙ্‌ক্তি
      দ্বিতীয় পঙ্‌ক্তি

              তৃতীয় পঙ্‌ক্তি

                           [প্রস্থান
```

Tesseract might produce separate blocks:

```text
block 1 → কবিতা
block 2 → প্রথম পঙ্‌ক্তি / দ্বিতীয় পঙ্‌ক্তি
block 3 → তৃতীয় পঙ্‌ক্তি
block 4 → [প্রস্থান
```

The fact that Tesseract assigns them `block_num = 1, 2, 3, 4` **does not mean you should treat those numbers as the canonical spatial reading order**.

In particular, centered and indented text can cause Tesseract's layout analysis to create blocks in ways that don't perfectly correspond to the literary flow.

### Recommended approach

Since your corpus is predominantly **single-column**, use a **top-to-bottom spatial ordering at the block/region level**.

Conceptually:

```python
regions.sort(key=lambda r: (r.top, r.left))
```

But there is an important improvement: **don't sort individual words purely by `top`**. First construct your `Region` objects from Tesseract's hierarchy, then sort the resulting regions.

A good pipeline is:

```text
Tesseract image_to_data
        ↓
group words
        ↓
(block_num, par_num, line_num)
        ↓
construct Region
        ↓
calculate Region bounding box
        ↓
sort Regions spatially
        ↓
reading order
```

For each region, calculate:

```text
region.top    = minimum(word.top)
region.bottom = maximum(word.top + word.height)
region.left   = minimum(word.left)
region.right  = maximum(word.left + word.width)
```

Then use the vertical position to establish the page flow.

Suppose two lines belong to the same stanza:


Their `top` values naturally differ, while their horizontal positions differ because of indentation/centering.

So I would recommend making the Tesseract block your initial region boundary:

```python

```

Then:

```python

```

This handles:

* centered headings
* indented poetry
* normally aligned prose
* right-aligned drama directions

without treating horizontal alignment as a change in reading sequence.

# 2. I would change your Y-band implementation slightly

This is the main thing I'd be careful about:

```python
band_ref_y = sum(b["center_y"] for b in bands[-1]) / len(bands[-1])
```

You're continuously moving the band's reference point.

That creates a **chaining effect**.

For example, with `y_tolerance = 5`:

```text
line A: y = 100
line B: y = 104
line C: y = 108
```

Your algorithm can potentially put all three in the same band:

```text
100 → 104 → 108
```

even though:

```text
abs(108 - 100) = 8 > 5
```

That could theoretically merge two actual literary lines into the same horizontal band.

For your corpus, I would make the band reference more stable.

For example:

```python
def _spatial_reading_order(
    lines: list[dict],
    y_tolerance: float,
) -> list[dict]:
    if not lines:
        return []

    by_y = sorted(lines, key=lambda ln: ln["center_y"])

    bands: list[list[dict]] = []
    band_ref_y: float | None = None

    for ln in by_y:
        if (
            band_ref_y is None
            or abs(ln["center_y"] - band_ref_y) > y_tolerance
        ):
            bands.append([ln])
            band_ref_y = ln["center_y"]
        else:
            bands[-1].append(ln)

    ordered: list[dict] = []

    for band in bands:
        band.sort(key=lambda ln: ln["x0"])
        ordered.extend(band)

    return ordered
```

Notice that I **don't update `band_ref_y`**.

That means a band represents a genuine vertical neighborhood around its first line rather than a potentially expanding cluster.

Assistant:
Because OCR does not guarantee that its line boundaries will be the same as the reference text's line boundaries.

Our reference and OCR can contain the same text, but organized into different numbers of lines.

Simple example

Suppose the reference says:

Reference line 1:
রবীন্দ্রনাথ ঠাকুর বাংলা সাহিত্যের একজন

Reference line 2:
বিশিষ্ট কবি ও সাহিত্যিক।

But OCR produces:

OCR line 1:
রবীন্দ্রনাথ ঠাকুর বাংলা সাহিত্যের

OCR line 2:
একজন বিশিষ্ট কবি ও সাহিত্যিক।

The OCR has effectively shifted the line boundary.

If we compare by position:

reference line 1 ↔ OCR line 1
reference line 2 ↔ OCR line 2

we get:

Reference: রবীন্দ্রনাথ ঠাকুর বাংলা সাহিত্যের একজন
OCR:       রবীন্দ্রনাথ ঠাকুর বাংলা সাহিত্যের

OCR:       একজন বিশিষ্ট কবি ও সাহিত্যিক।

Both lines appear to have errors, even though the OCR actually captured all the words correctly.

Instead of assuming:

reference[1] ↔ OCR[1]
reference[2] ↔ OCR[2]
reference[3] ↔ OCR[3]

Insertion → OCR has extra content
Deletion → OCR missed content
Line boundary differences → lines were split/merged

We could have used simpler alternatives.

Alternative 1 — positional comparison
R1 ↔ O1
R2 ↔ O2
R3 ↔ O3

Rejected: very fragile when OCR changes line boundaries.

Alternative 2 — independently find the closest OCR line

For every reference line, find the OCR line with the smallest edit distance.

Problem: two reference lines might both choose the same OCR line, and we lose the overall sequence structure.

Needleman–Wunsch considers the whole sequence and finds a globally consistent alignment using dynamic programming.

So the important idea is:

We aren't using Needleman–Wunsch because OCR text itself necessarily needs fuzzy matching. We're using it because the line boundaries between the reference and OCR output are not guaranteed to correspond.

That's the key reason for having the alignment stage in our pipeline.

And there's an important limitation we should discuss next: Needleman–Wunsch can also produce a wrong alignment, so alignment itself needs to be validated before we trust the resulting CER.

## 1. What CER measures

Let:

* **Reference** = the Internet Archive transcription, i.e. what the line should say.
* **Hypothesis** = your Tesseract `--psm 7 -l ben` output.

CER is:

[
\boxed{
CER = \frac{S + D + I}{N}
}
]

where:

* (S) = substitutions — wrong character
* (D) = deletions — OCR missed a character
* (I) = insertions — OCR added an extra character
* (N) = number of characters in the reference

This is essentially **Levenshtein edit distance divided by the reference length**.

### Example

Reference:

```text
আমার সোনার বাংলা
```

OCR:

```text
আমার শোনার বাংলা
```

Suppose one character is substituted:

```text
স → শ
```

Then:

[
CER = \frac{1}{16}
]

approximately `0.0625`, or **6.25%**.

Lower CER is better:

```text
CER = 0.00   → exact match
CER = 0.05   → very small difference
CER = 0.20   → substantial errors
CER = 1.00   → edit distance equals reference length
```

CER can even exceed `1.0` if there are many insertions.

## 7. Implement the Silver-Label Quality Gate

For every line, compare:

```text
Tesseract hypothesis
        ↕
correctly aligned Internet Archive reference
```

using **CER (Character Error Rate)**:

[
CER = \frac{S+D+I}{N}
]

where:

* `S` = substitutions
* `D` = deletions
* `I` = insertions
* `N` = number of reference characters

Lower CER means better agreement.

---

### 8. Normalize before CER calculation

Do not compare completely raw strings.

At minimum:

```python
unicodedata.normalize("NFC", text)
```

and normalize whitespace:

```python
re.sub(r"\s+", " ", text).strip()
```

This prevents harmless Unicode/whitespace differences from artificially increasing CER.

Do **not** aggressively normalize away Bengali characters, matras, conjuncts, punctuation, etc., because those are meaningful OCR errors.

---

### 9. Correct reference alignment is required

CER is only meaningful if the Tesseract line is compared against the **corresponding IA reference line**.

Do not blindly assume:

```text
Tesseract region #17 == IA line #17
```

unless your reference alignment guarantees that.

The intended flow is:

```text
Page
 ↓
IA reference
 ↓
reference-line alignment
 ↓
Tesseract Region ↔ IA reference line
 ↓
CER
```

If alignment fails, the line should not receive a misleading CER value.

Use an appropriate audit status such as:

```text
reference_alignment_failed
```

# 5. The biggest problem: reference alignment

This is the part I would change before relying on the Silver gate.

Your current method assumes:



Implement actual sequence alignment between the IA reference and detected OCR lines.

**For the current Stage 3 implementation, I recommend Option A.**

      ↓
OCR lines

User: Why use CER as the primary metric instead of WER??

Assistant:
Because CER (Character Error Rate) is a better fit for our Bengali OCR task than WER (Word Error Rate).

First, what are they measuring?

Both are based on edit distance.

CER:

CER=
N
S+D+I
	​


where:

S = character substitutions
D = character deletions
I = character insertions
N = number of characters in the reference

So if the reference is:

বাংলা

and OCR produces:

বাংগা

CER can detect that there is a character-level difference.

WER does the same basic idea, but treats an entire word as the unit.

Why CER fits our project better
1. OCR errors often happen inside words

Bengali OCR can make mistakes involving:

যুক্তাক্ষর
কার/মাত্রা
combining characters
individual glyphs
punctuation
character substitutions/deletions

Suppose:

Reference:
সাহিত্যের

OCR:
সাহিত্য

WER sees this roughly as:

Reference word: সাহিত্যের
OCR word:       সাহিত্য

→ one wrong word

It doesn't tell us much about how much of that word was actually wrong.

CER gives us a finer-grained measurement.

2. Bengali word boundaries aren't always the most useful unit

Our pipeline ultimately works with OCR text and line-level alignment.

We're already comparing:

reference line
      ↕
OCR line

So character-level distance naturally fits that evaluation.

The pipeline is essentially:

Reference lines
      ↕
Needleman–Wunsch alignment
      ↕
Aligned OCR lines
      ↓
Character-level comparison
      ↓
CER

CER therefore fits naturally after the alignment stage.

3. WER can exaggerate small OCR errors

Imagine:

Reference:
রবীন্দ্রনাথ

OCR:
রবীন্দ্রনাথ্

Suppose only one character/mark is incorrect.

At the word level, WER may effectively treat the entire word as incorrect.

CER gives us a more granular measurement of the actual textual difference.

So:

One small character error shouldn't necessarily be treated as an entirely incorrect word.

But why not use WER at all?

We shouldn't say WER is useless.

It's actually useful as a secondary metric.

For example:

Metric	What it tells us
CER	How many character-level errors OCR makes
WER	How many word-level errors OCR makes

CER is our primary metric because we're evaluating the quality of the OCR text at a fine-grained level.

WER could still provide an additional perspective.

There's also a practical reason

Our alignment is happening at the line level, and then we need to quantify how similar the aligned reference and OCR text are.

CER gives us a relatively continuous signal:

0% CER   → almost identical
5% CER   → small amount of corruption
20% CER  → substantial corruption
50% CER  → very poor OCR

That is useful when comparing preprocessing/OCR configurations.

With WER, a single character mistake can turn an otherwise correct word into a completely incorrect word.

Alternative we considered

We could have used WER as the primary metric.

Why we reject that as primary:
It is less granular.
Small character errors can make an entire word count as wrong.
Bengali OCR errors can occur within words.
Our line-level evaluation naturally fits character-level edit distance.
Chosen:

CER as primary + WER as a possible secondary metric.

One important caveat

CER isn't perfect either.

For Bengali, Unicode normalization and how we define a "character" matter a lot. If visually equivalent Bengali representations are encoded differently, we could artificially inflate CER.

So our evaluation needs consistent Unicode normalization before calculating the metric.

And there's another important limitation:

A low CER doesn't necessarily mean the OCR is perfect for RAG.

For example, if one important literary name is corrupted while everything else is correct, overall CER could still be low, but that particular error might seriously affect retrieval.

So the stronger evaluation story is:

CER
 ↓
overall OCR quality

+
line alignment
 ↓
where errors occur

+
retrieval metrics
 ↓
whether OCR quality actually affects RAG

+
citation/provenance
 ↓

- What worked well:

1.Using AI to discuss the pipeline stage-by-stage helped me understand why each component exists, instead of only focusing on whether the code works.

2.The discussion of Needleman–Wunsch alignment helped clarify why simple line-by-line comparison is unreliable when OCR inserts, deletes, splits, or merges lines.

3.Discussing CER vs WER helped me understand why CER is more suitable as the primary metric for Bengali OCR.

4.AI helped identify important edge cases and failure modes, such as blank pages, noisy scans, skewed pages, different numbers of reference/OCR lines, and repeated lines.

5.The discussion of OCR → retrieval → RAG failure propagation helped connect the OCR work to the final RAG system rather than treating OCR as an isolated component.

6.Discussing alternatives such as whole-page OCR, transformer OCR, exact line matching, and different alignment strategies helped me understand the trade-offs behind the chosen architecture.



- What didn't work / had to be fixed manually:

1.Some explanations initially oversimplified the actual pipeline flow, particularly the distinction between spatial reading-order processing in layout.py and reference/OCR line alignment in ocr.py.

2.Some architectural explanations were based on the conceptual pipeline rather than the exact implementation, so I had to verify them against the actual files.

3.There was a Tesseract PSM configuration mismatch. The discussion/checklist stated that Stage 2 used --oem 1 --psm 3, while the actual layout.py configuration was using PSM 4. After observing that PSM 4 was performing better on our scanned pages, I updated the configuration to use PSM 4 rather than following the earlier PSM 3 recommendation.

4.Also there was a major issue with the recommendation to use exact line-count matching. The assistant suggested requiring the reference and OCR output to have exactly the same number of lines. However, in practice, the line count often differs because OCR may split or merge lines, and enforcing exact equality meant that for many pages we could not obtain meaningful line-level CER/WER measurements at all. I therefore kept the fuzzy Needleman–Wunsch alignment with a small allowed line-count difference (max_line_diff=2), which allows reasonable OCR segmentation differences while still maintaining sequence alignment.

5.AI suggestions sometimes assumed that a component belonged to a separate stage/module when it was actually handled inside an existing file.

6.Some proposed approaches were too general and had to be adjusted to match the project's actual constraints, such as the existing contracts and metadata structure.

7.AI could suggest possible solutions, but the final decisions still required checking the implementation, tests, and project requirements manually.



- Anything I disagreed with or changed after using it:

I intentionally held off on jumping straight to a heavy transformer-based Bengali OCR model. Keeping Tesseract as our baseline gave us a lightweight, fully reproducible control, while leaving neural models like TrOCR open as a clear next step if we hit an accuracy ceiling.

Early on, I realized page-wide OCR wouldn't cut it—without layout awareness, you lose the reading order and line structure that our citation model depends on. That sequence structure also dictated our alignment choice: simple closest-line matching fails when lines get dropped or added, whereas a global Needleman–Wunsch DP alignment respects the actual sequential flow of the text.

When evaluating outputs, I prioritized CER over WER as the core metric, though tracking WER remains useful for readability. Instead of throwing out low-confidence or rejected OCR text, I routed that metadata into sidecars for auditing—silent failure is much worse than flagged dirty data.

Keeping document and page provenance strictly attached at every step wasn't just about retrieval filtering; it was essential for citation integrity. Ultimately, my perspective shifted: this isn't just an OCR pipeline—it’s an end-to-end information-preservation pipeline where an error in layout or text cascades straight into chunking, vector search, and final LLM grounding.
